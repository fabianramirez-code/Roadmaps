# JDK vs JRE vs JVM — qué contiene cada uno y por qué el JRE ya no se distribuye por separado


## Diferencias entre JVM, JRE, JDK
| | **JVM** | **JRE** | **JDK** |
|---|---|---|---|
| **Nombre** | Java Virtual Machine | Java Runtime Environment | Java Development Kit |
| **Función** | Ejecuta bytecode Java | Todo lo necesario para *ejecutar* una app Java | Todo lo necesario para *desarrollar* y ejecutar apps Java |
| **Contiene** | Motor de ejecución, class loader, JIT, GC | JVM + librerías de clases estándar | JRE + herramientas de desarrollo (`javac`, `jdb`, `javadoc`, `jlink`, etc.) |
| **Compila código** | No | No | Sí (`javac`) |
| **Quién lo usa** | Nadie lo instala por separado | Usuarios finales que solo ejecutan apps | Desarrolladores |

En resumen:

- JVM es el motor que carga, verifica y ejecuta el bytecode, gestiona memoria y hace garbage collection.  Es dependiente de plataforma (existe una implementación para cada OS/CPU).
- JRE = JVM + librerías de clases.  Es lo mínimo para correr un programa Java ya compilado.
- JDK = JRE + herramientas de desarrollo.  Es lo que instala un desarrollador.

> Nota importante: desde Java 9 (sistema de módulos) y especialmente desde Java 11, Oracle y OpenJDK ya no distribuyen un JRE separado.  El JDK es la única descarga estándar; si se necesita un runtime mínimo para una app, se genera con la herramienta `jlink`.

Que es la **JVM**?
Una maquina virtual de proceso nativo, ejecuta el codigo binario de bajo nivel generado por el propio compilador de Java.
- Aporta **portabilidad** permitiendo que las aplicaciones se ejecuten de manera independiente a el hardware y SO.
- Ademas se encarga de la gestion automatica de memoria con el **Garbage Collector**. Los objetos sin referencias se marcan como basura y se libera el espacio en memoria.

## **Garbage Collector (GC)**

Usa por defecto el algoritmo G1 (Garbage First), que divide el heap en regiones y prioriza las que tienen mas basura.

### Optimizacion
Ajustar el tamaño de la HEAP configurando `-Xms` (tamaño inicial del heap) y `-Xmx` (tamaño máximo del heap, el que más importa) con el mismo valor para evitar redimensionamientos dinámicos costosos.

`java -Xms512m -Xmx2g -jar app.jar`
- Unidades: k, m o g (por ejemplo -Xmx2g).

Para ver los valores por defecto de tu máquina:

`java -XX:+PrintFlagsFinal -version | findstr MaxHeapSize`

En **contenedores** (Docker, Kubernetes), es mejor usar un porcentaje de la RAM disponible, porque el límite de memoria del contenedor cambia entre entornos:

`java -XX:MaxRAMPercentage=75.0 -jar app.jar`

También se pueden definir las opciones con la variable de entorno **JAVA_TOOL_OPTIONS**, o en **"VM options"** de la configuración de ejecución del IDE.

*→ omitido: -Xmn y -XX:NewRatio (proporción entre generación joven y mayor), -XX:MaxMetaspaceSize (Metaspace está fuera del heap), y -Xms = -Xmx para evitar pausas por redimensionado. Úsalos cuando el perfilado (JFR, VisualVM) muestre un problema concreto.*

> Otros algoritmos del GC:
> - **Parallel GC:** Ideal para aplicaciones batch o procesamiento pesado donde importa más el rendimiento total (throughput) que las pausas cortas.
> - **ZGC / Shenandoah:** Shenandohan lo usa Java 21, ZGC lo usa Java 25 — Diseñados para latencias ultra bajas (milisegundos (ms) o microsegundos (μs)), ideales para sistemas de alta concurrencia en tiempo real.
>>Otras alternativas:
>> - **Memoria fuera del Heap (Off-Heap):** Uso de ByteBuffer.allocateDirect() o la API de Project Panama para gestionar memoria nativa manualmente y eludir el control del GC.
>> - **Patrones de reutilización (Object Pooling):** Reciclar objetos pesados para evitar asignaciones constantes.

## Tipos de Memoria
### 1. Heap (Montículo):
- Almacena todos los objetos e instancias creadas con new (incluyendo arrays).
- Compartido por todos los hilos (threads).
- Es el espacio gestionado por el GC.

### 2. JVM Stack (Pila):
- Almacena variables locales, frames de métodos y referencias a los objetos que viven en el Heap.
- Exclusivo para cada hilo (cada hilo tiene su propia pila).
- Su ciclo de vida está ligado al ámbito del método; se libera al salir de este.

### 3. Metaspace:
- Almacena los metadatos de las clases, estructuras internas, jerarquías y bytecode.
- A partir de Java 8, reside en la memoria nativa (off-heap) del sistema operativo, por lo que ya no está limitado por el tamaño del Heap tradicional.

### 4. PC Register (Registro de Contador de Programa):
- Exclusivo por hilo; almacena la dirección de la instrucción de bytecode que se está ejecutando actualmente.

### 5. Native Method Stack:
- Similar al Stack de la JVM, pero optimizado para ejecutar código nativo (escrito en C/C++) mediante JNI (Java Native Interface).
