# Cadencia de releases — un release cada seis meses (marzo y septiembre), JEP 322 (Java 10)

### JEP 322
Introdujo en Java 10 (marzo de 2018) una cadencia de lanzamientos de seis meses para reemplazar el modelo anterior de años.  Bajo este esquema, se publican lanzamientos de características cada seis meses, específicamente en marzo y septiembre, con el número de versión principal incrementándose en cada ciclo.

- Las versiones intermedias (no LTS) reciben soporte solo hasta el siguiente lanzamiento,

- Las versiones de Soporte a Largo Plazo (LTS) se designan con mayor frecuencia para garantizar estabilidad empresarial; actualmente, Oracle designa una LTS cada dos años (siguiendo las series 17, 21, 25). Este modelo permite que las características se entreguen de forma predecible y rápida, sin esperar a que un proyecto complejo como Jigsaw retrasara todo el lanzamiento.

# Política LTS — LTS cada dos años: 8, 11, 17, 21, 25, próximo 29 (sept 2027)

La política de Soporte a Largo Plazo (LTS) de Java establece que se lanza una versión LTS cada dos años, específicamente cada cuarta versión general (que salen cada seis meses).  
> Las versiones LTS confirmadas son Java 8, 11, 17, 21 y 25, y la próxima versión LTS es Java 29, prevista para septiembre de 2027.

Detalles clave de la cronología:

- **Frecuencia**: Desde Java 17, Oracle mantiene un calendario estricto donde una versión LTS se designa cada dos años, mientras que las versiones intermedias (como Java 26 o 27) tienen un soporte limitado de solo seis meses.
- **Cobertura de soporte**: Las versiones LTS reciben parches de seguridad y actualizaciones durante un periodo extendido, que según el calendario de Oracle incluye soporte premier y extendido hasta septiembre de 2033 para Java 25 y septiembre de 2035 para Java 29.
- **Recomendación actual**: Para nuevos proyectos, se recomienda utilizar Java 25 (la última LTS disponible), mientras que para producción se debe elegir una versión LTS para garantizar la estabilidad y el mantenimiento a largo plazo.

# Proceso JEP / JCP / OpenJDK — quién propone, quién aprueba, qué es una JSR

- **Propuestas**: Las Java Specification Requests (JSR) son propuestas formales enviadas por miembros de la Java Community Process (JCP), que incluyen corporaciones e individuos.  Los JDK Enhancement Proposals (JEP) son propuestos por conmutadores (committers) de OpenJDK y desarrolladores de la comunidad.
- **Aprobación**: El Comité Ejecutivo (EC) del JCP es el órgano que aprueba y vota las JSRs para su estandarización.  La dirección de OpenJDK (OpenJDK Lead) es quien decide qué JEPs se aceptan y se incluyen en el mapa de ruta de las versiones del JDK.

- **Qué es una JSR**: Una JSR es un documento formal que define nuevas especificaciones, APIs o cambios en la plataforma Java.  Cada JSR produce una especificación oficial, una Implementación de Referencia (RI) (usualmente en OpenJDK) y un Kit de Compatibilidad de Tecnología (TCK) para garantizar la conformidad de las implementaciones.
