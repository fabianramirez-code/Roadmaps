# WORA (write once, run anywhere) — cómo lo logran bytecode y JVM; sus límites reales

El principio **WORA** (Write Once, Run Anywhere): Se logra mediante la compilación del código fuente en bytecode, un formato de instrucciones neutro y estandarizado, que es ejecutado por la JVM (Java Virtual Machine).  

La JVM actúa como una capa de abstracción que traduce este bytecode en instrucciones nativas específicas para el sistema operativo y la arquitectura de hardware del dispositivo, **permitiendo que el mismo archivo binario funcione en diferentes plataformas sin necesidad de recompilación**.

## Los límites reales de esta portabilidad incluyen:
- **Interfaz Nativa (JNI)**: El uso de bibliotecas nativas (como archivos .dll o .so) rompe la portabilidad, ya que estos binarios son específicos de la arquitectura y el sistema operativo.
- **Diferencias del Sistema Operativo**: A pesar del bytecode, el código puede fallar si asume detalles específicos de un SO, como rutas de archivos, permisos o manejo de procesos.
- **Rendimiento y Compatibilidad**: La JVM introduce sobrecarga por interpretación y recolección de basura, y las diferencias en la implementación de la JVM o la versión de la biblioteca estándar pueden causar comportamientos inconsistentes entre plataformas.

### Bytecode
> Es un conjunto de instrucciones intermedias, un nivel por encima del código máquina nativo y uno por debajo del código fuente. Cada instrucción se codifica en un solo byte (de ahí el nombre) más opcionalmente operandos.
>
> Características clave:
>
> - **Independiente de plataforma**: no está dirigido a una CPU concreta, sino a la JVM. El mismo .class corre en Windows, Linux o ARM sin cambios.
> - **Basado en pila**: a diferencia de las CPUs reales (que usan registros), la JVM opera sobre una pila de operandos. Las instrucciones empujan (push) y sacan (pop) valores de esa pila.
>
>> Ejemplo:
>>```java
>>static int add(int a, int b) { return a + b; }
>>```
>>se compila a:
>>```bytecode
>>iload_0      // push 'a' en la pila
>>iload_1      // push 'b' en la pila
>>iadd         // pop ambos, push la suma
>>ireturn      // pop el resultado y devolverlo
>>```
> **Ejecución**: la JVM carga el bytecode, lo verifica (seguridad), y lo ejecuta ya sea interpretando instrucción por instrucción o pasando los "hot paths" al compilador JIT que los traduce a código nativo.
>
> **En resumen**: bytecode es el "lenguaje de ensamblador" de la JVM — compacto, portable y lo suficientemente abstracto para que solo la JVM necesite ser portada, no el código de la aplicación.

### Hot paths (métodos "calientes")
> Son los métodos y bucles que el programa ejecuta muchas veces. La JVM los detecta con dos contadores:
>
> **Invocation counter**: cuántas veces se llama el método.
> **Back-edge counter**: cuántas veces se repite un bucle (rama hacia atrás en el bytecode).
> Cuando un método cruza un umbral (por defecto ~10 000 invocaciones o ~1 000 iteraciones de bucle), se marca como hot y se encola para compilación. 
> 

### El compilador JIT

> **JIT = Just-In-Time**: Es el componente de la JVM que traduce bytecode a código nativo de la CPU mientras el programa corre, usando los datos de profiling recolectados en tiempo de ejecución.
>
>**Tiered Compilation (5 niveles)**
>| Nivel | Qué corre | Rol |
>|-------|-----------|-----|
>| 0 | Interpreter | Arranque; cuenta invocaciones y back-edges |
>| 1 | C1, sin profiling | Métodos triviales (getters) que no merecen más |
>| 2 | C1, profiling ligero | Atajo cuando la cola de C2 está saturada |
>| 3 | C1, **profiling completo** | Recoge tipos de receiver, ramas, frecuencias |
>| 4 | **C2** (o Graal) | Optimización agresiva: inlining, escape analysis, unrolling, vectorización |
>
>La ruta típica es 0 → 3 → 4: el intérprete detecta el hot method, C1 lo compila rápido con profiling, y C2 lo recompila con todo el conocimiento acumulado para rendimiento máximo.

### Optimizaciones clave de C2
> - **Inlining**: expande el cuerpo de métodos pequeños dentro del caller, eliminando el overhead de la llamada y exponiendo el código a más optimizaciones.
> - **Devirtualización**: si el perfil dice que un sitio de llamada siempre recibe el mismo tipo, emite una llamada directa en vez de una búsqueda virtual.
> - **Escape analysis**: si un objeto no "escapa" del método, lo aloja en la pila o directamente en registros, evitando la GC.
> - **Deoptimización**: si una suposición (ej. "este sitio siempre recibe String") resulta falsa, el código compilado se descarta y vuelve al intérprete para recompilar con datos correctos.

###  C1 vs C2 en resumen
>| | C1 (Client) | C2 (Server) |
>|--|-------------|-------------|
>| Velocidad de compilación | ~1–5 ms | ~50–500 ms |
>| Optimización | Básica | Agresiva |
>| Ideal para | Arranque, apps cortas | Servidores, long-running |

### Graal
> Es una reescritura del tier (nivel) 4 en Java (vía JVMCI) con una IR gráfica de lenguaje neutro. En GraalVM reemplaza a C2 por defecto y permite además compilar ahead-of-time a binario nativo (native-image), eliminando el warmup.
>
> **En esencia**: el JIT convierte el "pago por interpretación" en un warmup inicial a cambio de que, una vez calientes, los hot paths rindan igual o mejor que C++ compilado estáticamente.
