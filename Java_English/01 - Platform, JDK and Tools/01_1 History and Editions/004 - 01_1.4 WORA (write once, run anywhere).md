# WORA (write once, run anywhere) — how bytecode and the JVM achieve it; real limitations

The **WORA** (Write Once, Run Anywhere) principle: Achieved by compiling source code into bytecode, a neutral, standardized instruction format executed by the JVM (Java Virtual Machine).

The JVM acts as an abstraction layer that translates this bytecode into native instructions specific to the device's operating system and hardware architecture, **allowing the same binary file to work on different platforms without recompilation**.

## Real limitations of this portability include:
- **Native Interface (JNI)**: Using native libraries (such as .dll or .so files) breaks portability because these binaries are specific to an architecture and operating system.
- **Operating system differences**: Despite bytecode, code can fail if it assumes OS-specific details such as file paths, permissions or process handling.
- **Performance and compatibility**: The JVM introduces interpretation and garbage-collection overhead, and differences in JVM implementations or standard-library versions can cause inconsistent behavior across platforms.

---

### Bytecode
> A set of intermediate instructions, one level above native machine code and one below source code. Each instruction is encoded in a single byte (hence the name), optionally followed by operands.
>
> Key characteristics:
>
> - **Platform-independent**: Targets the JVM, not a specific CPU. The same .class runs unchanged on Windows, Linux or ARM.
> - **Stack-based**: Unlike real CPUs (which use registers), the JVM operates on an operand stack. Instructions push values onto and pop values off this stack.
>
>> Example:
>>```java
>>static int add(int a, int b) { return a + b; }
>>```
>>compiles to:
>>```bytecode
>>iload_0      // push 'a' onto the stack
>>iload_1      // push 'b' onto the stack
>>iadd         // pop both, push their sum
>>ireturn      // pop and return the result
>>```
> **Execution**: The JVM loads and verifies the bytecode (security), then executes it either by interpreting it instruction by instruction or by passing the "hot paths" to the JIT compiler, which translates them into native code.
>
> **In summary**: Bytecode is the JVM's "assembly language" — compact, portable and abstract enough that only the JVM needs porting, not the application code.

### Hot paths ("hot" methods)
> Methods and loops that the program executes many times. The JVM detects them with two counters:
>
> **Invocation counter**: How many times a method is called.
> **Back-edge counter**: How many times a loop repeats (a backward branch in bytecode).
> When a method crosses a threshold (by default ~10,000 invocations or ~1,000 loop iterations), it is marked hot and queued for compilation.
>

### The JIT compiler

> **JIT = Just-In-Time**: The JVM component that translates bytecode into native CPU code while the program runs, using profiling data collected at runtime.
>
>**Tiered Compilation (5 levels)**
>| Level | What runs | Role |
>|-------|-----------|-----|
>| 0 | Interpreter | Startup; counts invocations and back-edges |
>| 1 | C1, no profiling | Trivial methods (getters) not worth further effort |
>| 2 | C1, light profiling | Shortcut when the C2 queue is saturated |
>| 3 | C1, **full profiling** | Collects receiver types, branches, frequencies |
>| 4 | **C2** (or Graal) | Aggressive optimization: inlining, escape analysis, unrolling, vectorization |
>
>The typical path is 0 → 3 → 4: the interpreter detects the hot method, C1 compiles it quickly with profiling, and C2 recompiles it with all accumulated knowledge for maximum performance.

### Key C2 optimizations
> - **Inlining**: Expands the bodies of small methods inside the caller, eliminating call overhead and exposing code to more optimizations.
> - **Devirtualization**: If the profile shows a call site always receives the same type, emits a direct call instead of a virtual lookup.
> - **Escape analysis**: If an object does not "escape" its method, allocates it on the stack or directly in registers, avoiding GC.
> - **Deoptimization**: If an assumption (e.g. "this site always receives String") proves false, compiled code is discarded and execution returns to the interpreter to recompile with correct data.

### C1 vs C2 in summary
>| | C1 (Client) | C2 (Server) |
>|--|-------------|-------------|
>| Compilation speed | ~1–5 ms | ~50–500 ms |
>| Optimization | Basic | Aggressive |
>| Ideal for | Startup, short-lived applications | Servers, long-running applications |

### Graal
> A rewrite of tier (level) 4 in Java (via JVMCI) with a language-neutral graphical IR. In GraalVM it replaces C2 by default and also supports ahead-of-time compilation into a native binary (native-image), eliminating warmup.
>
> **In essence**: The JIT trades the "cost of interpretation" for initial warmup so that, once hot, hot paths perform as well as or better than statically compiled C++.
