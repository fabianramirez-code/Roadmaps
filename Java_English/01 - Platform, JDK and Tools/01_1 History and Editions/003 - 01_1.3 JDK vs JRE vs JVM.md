# JDK vs JRE vs JVM — what each contains and why the JRE is no longer distributed separately


## Differences between JVM, JRE, JDK
| | **JVM** | **JRE** | **JDK** |
|---|---|---|---|
| **Name** | Java Virtual Machine | Java Runtime Environment | Java Development Kit |
| **Function** | Runs Java bytecode | Everything needed to *run* a Java application | Everything needed to *develop* and run Java applications |
| **Contains** | Execution engine, class loader, JIT, GC | JVM + standard class libraries | JRE + development tools (`javac`, `jdb`, `javadoc`, `jlink`, etc.) |
| **Compiles code** | No | No | Yes (`javac`) |
| **Who uses it** | Nobody installs it separately | End users who only run applications | Developers |

In summary:

- JVM is the engine that loads, verifies and executes bytecode, manages memory and performs garbage collection. It is platform-dependent (there is an implementation for each OS/CPU).
- JRE = JVM + class libraries. It is the minimum needed to run an already compiled Java program.
- JDK = JRE + development tools. This is what a developer installs.

> Important note: Since Java 9 (the module system), and especially since Java 11, Oracle and OpenJDK no longer distribute a separate JRE. The JDK is the only standard download; if an application needs a minimal runtime, generate one with `jlink`.

What is the **JVM**?
A native-process virtual machine that runs the low-level binary code generated by the Java compiler itself.
- It provides **portability** by allowing applications to run independently of hardware and the operating system.
- It also manages memory automatically with the **Garbage Collector**. Objects without references are marked as garbage and their memory is freed.

---

## **Garbage Collector (GC)**

By default, it uses the G1 (Garbage First) algorithm, which divides the heap into regions and prioritizes those with the most garbage.

### Optimization
Set the heap size with `-Xms` (initial heap size) and `-Xmx` (maximum heap size, the more important one), using the same value to avoid costly dynamic resizing.

`java -Xms512m -Xmx2g -jar app.jar`
- Units: k, m or g (for example, -Xmx2g).

To view your machine's default values:

`java -XX:+PrintFlagsFinal -version | findstr MaxHeapSize`

In **containers** (Docker, Kubernetes), using a percentage of available RAM is better because the container memory limit changes between environments:

`java -XX:MaxRAMPercentage=75.0 -jar app.jar`

You can also define options with the **JAVA_TOOL_OPTIONS** environment variable or in the IDE run configuration's **"VM options"**.

*→ omitted: -Xmn and -XX:NewRatio (ratio between young and old generations), -XX:MaxMetaspaceSize (Metaspace is outside the heap), and -Xms = -Xmx to avoid resizing pauses. Use these when profiling (JFR, VisualVM) reveals a specific problem.*

> Other GC algorithms:
> - **Parallel GC:** Ideal for batch applications or heavy processing where overall throughput matters more than short pauses.
> - **ZGC / Shenandoah:** Shenandoah is used by Java 21, ZGC by Java 25 — designed for ultra-low latency (milliseconds (ms) or microseconds (μs)), ideal for high-concurrency real-time systems.
>>Other alternatives:
>> - **Off-heap memory:** Use `ByteBuffer.allocateDirect()` or the Project Panama API to manage native memory manually and bypass GC control.
>> - **Reuse patterns (Object Pooling):** Recycle expensive objects to avoid constant allocations.

## Memory Types
### 1. Heap:
- Stores all objects and instances created with `new` (including arrays).
- Shared by all threads.
- Managed by the GC.

### 2. JVM Stack:
- Stores local variables, method frames and references to objects on the heap.
- Exclusive to each thread (each thread has its own stack).
- Its lifecycle follows method scope; it is freed when the method exits.

### 3. Metaspace:
- Stores class metadata, internal structures, hierarchies and bytecode.
- Since Java 8, it resides in the operating system's native (off-heap) memory, so the traditional heap size no longer limits it.

### 4. PC Register (Program Counter Register):
- Exclusive to each thread; stores the address of the bytecode instruction currently being executed.

### 5. Native Method Stack:
- Similar to the JVM Stack, but optimized to execute native code (written in C/C++) via JNI (Java Native Interface).
